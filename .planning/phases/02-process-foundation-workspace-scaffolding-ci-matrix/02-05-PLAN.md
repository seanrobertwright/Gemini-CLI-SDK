    The real false positive: The grep finds `it('close'` — this must come from a line like `child.on('close', (code) => {` where grep's `-o` flag extracts `it('close'` from the substring `emit('close'` or similar. Actually checking the TS source, SpawnPerCallStrategy.spec.ts line 117 has `child.on('close', (code) => {`. The pattern `(test|it)\(['\"][^'\"]+['\"]` matches the substring `it('close'` from within the string `...it('close', ...` — the two characters `it` appear before `('close'`.

    Wait — `child.on('close', ...)` — the `n(` before `'close'` means the ERE `(test|it)\(` would NOT match `on(`. Let me reconsider. The grep uses `-oE` which finds all matches on a line. Looking at `child.on('close', (code) => {` — there is no `test(` or `it(` substring in this string. But the TS test file IS a `.spec.ts` file being searched with `grep -rh`.

    Actually the output shows 25 sorted TS names including `close`. Looking more carefully at the grep output, this might come from a different line. The key thing: the grep `-oE` finds overlapping patterns anywhere in the file. Let me check ProcessManager.spec.ts which has `child.on('close', () => resolve());`. The letters `it` don't appear before `(` in `on('close'`. But wait — maybe it matches `it('close'` from some describe block context.

    Actually, on re-analysis: grep `-oE` finds `(test|it)\(['\"][^'\"]+['\"]` which requires literal `test(` or `it(` followed by a quote. The word `it` followed by `(` and `'close'` could occur if there's a test called `it('close'...)` somewhere. But checking the files, there isn't one. The most likely explanation: grep is finding a match across the boundary of `emit('close'` where `...emit('close'...` contains the substring `it('close'`.
