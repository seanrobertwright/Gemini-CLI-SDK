    Derive the schema by walking every line of every captured NDJSON fixture, collecting the set of observed event types and the fields that appear on each. Then author `spec/events.schema.json` as a JSON Schema 2020-12 discriminated union with one `$defs` entry per observed type.

    **Algorithm (implement as an inline Node one-liner via Bash, or a temporary `.mjs` that you delete after):**

    1. Read all 12 fixture files under `spec/fixtures/*.ndjson`. For each file, split by `\r?\n`, skip empty lines, `JSON.parse` each line.

    2. Group parsed events by `type` field value. If an event has no `type` (shouldn't happen for real gemini output but possible for cli_log lines), skip it for schema derivation purposes — it's not an event.

    3. For each type group, accumulate the union of field names observed (not including `type` itself). Record which fields appear in ALL events of that type (required) vs. SOME events (optional). Record a lightweight type guess for each field: `string`, `number`, `boolean`, `object`, `array`, `null`, or `string|null` etc. (Use `typeof` + array/null checks.)

    4. Include the synthetic `cosmic_ray_hit` type from `event-unknown.ndjson` in the derived set — but annotate its $defs entry with a comment field indicating it's synthetic. Actually: skip the synthetic type because the whole point is that the parser's `unknown` fallback handles it WITHOUT a schema match. The schema should NOT include `cosmic_ray_hit` as a known variant.

    5. Author `spec/events.schema.json` with this structure:

    ```json
    {
      "$schema": "https://json-schema.org/draft/2020-12/schema",
      "$id": "https://gemini-sdk.dev/spec/events.schema.json",
      "title": "Gemini CLI stream-json event",
      "description": "Discriminated union of all event types observed in spec/fixtures/ captured against gemini-cli <VERSION>. Each $defs entry represents ONE observed event type. Every entry sets additionalProperties:true so the parser tolerates upstream field additions. The schema is a FLOOR of known fields, not a ceiling. Unknown types are handled by the parser's lenient fallback, not by this schema.",
      "oneOf": [
        { "$ref": "#/$defs/InitEvent" },
        { "$ref": "#/$defs/MessageEvent" },
        // ... one $ref per observed type
      ],
      "$defs": {
        "InitEvent": {
          "type": "object",
          "required": ["type"],
          "properties": {
            "type": { "const": "init" },
            "session_id": { "type": "string" },
            "model": { "type": "string" }
            // ... all observed fields
          },
          "additionalProperties": true
        }
        // ... one def per observed type
      }
    }
    ```

    6. Replace `<VERSION>` in the description with the actual pinned version read from `.gemini-cli-compat`.

    7. Write the schema to `spec/events.schema.json` using the Write tool (overwriting the empty-oneOf seed from plan 01-01).

    **Important rules:**
    - Every `$defs` entry MUST have `additionalProperties: true` (RESEARCH.md §"Pattern 1" critical design rule).
    - Every `$defs` entry MUST have `required: ["type"]` at minimum — the discriminator field is the ONLY field we hard-require, because upstream may make other fields optional in future releases.
    - The `type` property in every entry MUST use `{ "const": "<typename>" }` (not `enum: ["<typename>"]`) — this is the form both codegen tools understand as a discriminator.
    - PascalCase the `$defs` entry names: `init` → `InitEvent`, `message` → `MessageEvent`, `tool_use` → `ToolUseEvent`, etc.
    - If a field has inconsistent types across events (e.g., `error.code` is sometimes a number and sometimes a string), use `oneOf: [{type: 'string'}, {type: 'number'}]` at the field level.
    - If a field is obviously a nested object (e.g., `usage: {prompt_tokens: 12, completion_tokens: 47}`), recurse one level deep but don't over-schema — leave nested objects as `{ type: 'object', additionalProperties: true }` unless the fields are clearly stable.

    **One-shot derivation script (run via Bash, delete after):**

    Write a temporary `scripts/_derive-schema.mjs` that implements the algorithm above, run it, verify the output, then either delete `_derive-schema.mjs` OR keep it if it's useful for re-derivation on future fixture changes. Recommendation: keep it, rename to `scripts/derive-schema.mjs` (no underscore prefix), and include it in this plan's `files_modified` if kept. If kept, it should read fixtures and print the schema to stdout; a separate command redirects to `spec/events.schema.json`.

    For simplicity in this plan, run the derivation inline and just write the final schema. If you keep the derivation script, add it as a bonus artifact but do not rely on re-running it for validation — the committed `spec/events.schema.json` IS the source of truth going forward.
