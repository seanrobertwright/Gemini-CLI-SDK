    **Helper 1: `async function smokeResumeMatrix()`** — Runs the 9-cell matrix from RESEARCH.md Pitfall #2. Each cell is a subprocess invocation:

    - Three prompt modes:
      - `positional`: `['prompt text goes here', '--output-format', 'stream-json']` (first positional arg)
      - `stdin`: `['--output-format', 'stream-json']` with prompt piped to child stdin
      - `dashP`: `['-p', 'prompt text goes here', '--output-format', 'stream-json']`
    - Three session modes:
      - `fresh`: no `--resume` flag
      - `resume-latest`: `['--resume', 'latest']` prepended
      - `resume-id`: `['--resume', '<captured-id>']` prepended where `<captured-id>` is the `session_id` from a prior `fresh + dashP` invocation

    For each of the 9 cells, spawn `gemini` (shell: false, windowsHide: true), wait up to 30s, and classify the result:
    - `PASS`: exit code 0 AND stdout contains at least one valid JSON line with `"type":"message"` or `"type":"result"`
    - `FAIL`: exit code non-zero OR stdout contains only error events OR times out
    - Record the stderr tail (first 500 chars, redacted) for each FAIL cell

    Return a matrix object:
    ```javascript
    {
      cells: [
        { prompt_mode: 'positional', session_mode: 'fresh', result: 'PASS' | 'FAIL', stderr_tail: '...' },
        // ... 9 entries
      ],
      verdict: 'pass' | 'fail' | 'partial'  // 'pass' = all 9 pass; 'fail' = all 9 fail; 'partial' = mixed
    }
    ```

    **Helper 2: `async function smokeConfigDir()`** — Tests GEMINI_CONFIG_DIR isolation on Windows. Steps:

    1. Read the current `~/.gemini/settings.json` mtime (if it exists). Record it.
    2. Create a temp directory with `fs.mkdtempSync(path.join(os.tmpdir(), 'gemini-cfg-'))`.
    3. Write a distinctive stub file there: `<tempdir>/settings.json` containing `{"_phase1_probe": true}`.
    4. Spawn `gemini -p "hello" --output-format stream-json` with `env = { ...process.env, GEMINI_CONFIG_DIR: <tempdir> }`.
    5. After the child exits, re-read the real `~/.gemini/settings.json` mtime and compare — it MUST be unchanged (if it changed, gemini-cli wrote to the real settings file, which is a violation).
    6. Also check: did `<tempdir>/settings.json` get modified or read? A file-access check via `fs.stat().atime` before/after is unreliable on Windows; instead, run gemini with a verbose/debug flag if available, or compare whether the child's subsequent behavior reflects the stub settings.
    7. Try the same test with `HOME` override: `env = { ...process.env, HOME: <tempdir>, USERPROFILE: <tempdir> }`.
    8. Try the fallback mechanism: `gemini mcp add --scope project --command fake-mcp` inside a fresh temp `cwd` and check if a local `./.gemini/settings.json` gets created.

    Classify:
    - `pass`: GEMINI_CONFIG_DIR works AND real `~/.gemini/settings.json` mtime unchanged
    - `fail`: GEMINI_CONFIG_DIR ignored AND no fallback works
    - `partial`: GEMINI_CONFIG_DIR ignored BUT `gemini mcp add --scope project` works (Phase 9 will use this fallback)

    Return:
    ```javascript
    {
      gemini_config_dir_respected: boolean,
      home_override_respected: boolean,
      mcp_add_scope_project_works: boolean,
      real_settings_mtime_unchanged: boolean,
      verdict: 'pass' | 'fail' | 'partial',
      details: '...'
    }
    ```

    **Helper 3: `async function smokeFlushTiming()`** — Measures inter-line arrival times for a long output. Steps:

    1. Reference run (short): spawn `gemini -p "Say hello." --output-format stream-json`. Record `process.hrtime.bigint()` at each stdout line arrival. Compute arrival-delta distribution.
    2. Long run: spawn `gemini -p "List 200 distinct facts about octopuses, one per line, numbered." --output-format stream-json`. Same timing capture.
    3. Measure:
       - Total stdout byte count for long run (must be >64 KB to exceed Node default pipe buffer; if it's under 64 KB, the test is inconclusive and we retry with a longer prompt)
       - Max inter-line gap (ms)
       - Count of inter-line gaps that exceed 500 ms (each such gap is a potential flush boundary)
       - Bursty pattern detection: if 80%+ of lines arrive in 2-3 clumps with large gaps between clumps, block-buffering is likely

    Classify:
    - `pass`: Long run has inter-line gaps consistent with the short reference (no bursty pattern), meaning per-event flushing works
    - `fail`: Long run shows 2-3 large clumps matching 64 KB block boundaries; forcePty fallback needed in Phase 4
    - `partial`: Some bursty pattern but not clearly block-buffered (may be model latency, not pipe buffer)

    Return:
    ```javascript
    {
      short_run_bytes: number,
      long_run_bytes: number,
      short_run_inter_line_p95_ms: number,
      long_run_inter_line_p95_ms: number,
      long_run_large_gaps: number,  // count of gaps > 500ms
      bursty: boolean,
      verdict: 'pass' | 'fail' | 'partial',
      details: '...'
    }
    ```
