    **1. Abort-midstream logic:**

    Add support for the `scenario.abortAtMs` field. When set, the handler:
    - Starts the child process normally
    - Schedules a `setTimeout` for `abortAtMs` milliseconds
    - When the timeout fires, sends SIGTERM on POSIX / `taskkill /T /F /PID <pid>` on Windows
    - Continues draining stdout until the child actually exits (it will shortly after the signal)
    - Writes whatever NDJSON arrived, including a partial final line if truncated (do NOT pad or repair)
    - Records `aborted: true` and the elapsed time in the `.expected.json`

    Windows note from RESEARCH.md: `proc.kill('SIGTERM')` on Windows just kills the top-level process but MAY leave MCP grandchildren — that's OK for this fixture because gemini with a simple prompt doesn't spawn grandchildren. For pedantic correctness, on Windows use:
    ```javascript
    import { execSync } from 'node:child_process';
    // ... when aborting:
    if (process.platform === 'win32') {
      try { execSync(`taskkill /T /F /PID ${proc.pid}`); } catch {}
    } else {
      proc.kill('SIGTERM');
      setTimeout(() => { if (!proc.killed) proc.kill('SIGKILL'); }, 5000);
    }
    ```

    **2. Large-output handling:**

    The large-output scenario already has `timeoutMs: 180000` from plan 01-03. Confirm the handler respects this and doesn't truncate early. Also confirm the stdout drain accumulates in memory safely up to ~256 KB (the target is >128 KB per RESEARCH.md Pitfall #4).
